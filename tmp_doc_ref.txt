1. Problem Statement Recap
Official framing (Ministry of Home Affairs, I4C, CIS Division):
The National Cybercrime Reporting Portal (NCRP) receives approximately 8,000 complaints daily, a number rising month over month. The current system is reactive — complaints are filed, then investigated. This project asks for a predictive framework that forecasts likely cash-withdrawal locations in advance, enabling law enforcement (coordinated by I4C) and banks/financial institutions to intervene proactively — deploying teams, alerting banks/ATMs, and freezing funds faster.

2. One-Line Pitch & Core Idea
“Four victims in four states can file four separate complaints and never know they were scammed by the same syndicate. Setu connects them, predicts where the money is headed, tells every relevant jurisdiction at once, and lets an unrelated bank flag the same threat — all before the money is gone.”
Full pitch: A system that ingests a cybercrime complaint the moment it's filed, checks whether it's secretly linked to other complaints (revealing hidden syndicates), predicts where and roughly when the stolen money will be cashed out, prioritizes it against every other open case, routes the alert to the correct jurisdiction(s) automatically, logs a tamper-evident fraud flag other banks can check without seeing raw data, and explains every decision it makes in plain language.
Working name
Project Setu — "setu" (bridge) — because the core value is bridging isolated complaints into connected intelligence, and bridging LEAs/banks across jurisdictions.
3. Why This Approach — The Real-World Gap
Today: a victim gets defrauded, files a complaint on NCRP, and by the time an officer reviews it, the money has typically already hopped through 3–5 mule accounts and been withdrawn in cash — often in a small number of well-documented districts. The complaint becomes a paperwork trail, not an intervention.
Setu flips this by using patterns from past fraud cases to predict the next case's cash-out point while a window for action still exists, and by surfacing hidden connections between complaints that no single officer would otherwise see.
Important framing: This is a decision-support and coordination-speed tool. It does not claim to autonomously freeze funds, guarantee recovery, or replace human/legal authority at any point. Every output is a recommendation or a drafted request for a human to act on.
4. Full End-to-End Flow
Victim's bank, amount, fraud type, timestamp, and suspect-side identifiers (receiving account/IFSC, phone, UPI ID, device ID if available) are captured — mirrors what NCRP already collects.
Checks if any suspect-side identifier has appeared in other complaints (any state, any officer, any date). If matched, this complaint joins an existing syndicate cluster in the graph database.
Two-tier model predicts top-3 likely withdrawal locations, a confidence score, and an urgency countdown (minutes until likely cash-out). Cluster history boosts confidence when available.
Case is ranked against all open cases using urgency, log-scaled recoverable amount, and cluster-size bonus — not raw amount alone.
Determines every relevant jurisdiction (victim location, suspect account branch location, predicted withdrawal location, plus jurisdictions of any linked complaints) and splits the alert accordingly.
Real email/SMS (SendGrid/Twilio) fires to the routed jurisdiction(s), gated by a confidence/urgency threshold to avoid alert fatigue.
Suspect identifiers are HMAC-hashed and logged on a permissioned ledger with a mandatory complaint reference. Any participating bank can query flag status without seeing raw data.
Every alert shows the real reasoning: which identifiers matched, which cluster, which feature drove the prediction — pulled from the model's actual feature importances.
Aggregates ₹ value flagged as recoverable, syndicate clusters surfaced, and alert-to-routing time — all labeled as simulated/synthetic.
The victim can separately check a simple, honest status page showing a recovery-odds indicator — without exposing internal cluster, jurisdiction, or ledger data.
5. System Architecture
Queue-based ingestion feeding a set of stateless workers, backed by three purpose-fit data stores (relational, graph, ledger) because the three data shapes involved are genuinely different.
[Complaint Form / Mock NCRP API]        |        v[Ingestion API] --> [Message Queue] --> [Correlation Worker] --> [Graph DB]                                              |                                              v                                     [Prediction Worker] --> [Model Store]                                              |                                              v                                     [Prioritization Worker] --> [Relational DB]                                              |                                              v                                     [Jurisdiction Router] --> [Alert Service] --> Email/SMS                                              |                                              v                                     [Ledger Writer] --> [Permissioned Ledger]                                              |                                              v                                     [Explainability Service]                                              |                                              v                            [Dashboard API] --> [Officer Portal / Citizen Portal]
Why queue-based: If the prediction worker or graph DB is momentarily slow, the ingestion API shouldn't block or drop complaints. A queue decouples "a complaint arrived" from "all the processing that happens to it," and is the honest basis for the scaling claim (see Section 9 — no load testing has actually been performed).

6. Data Layer — Synthetic Dataset Strategy
Reality check: Real NCRP complaint data is confidential MHA/I4C data and will not be accessible. The dataset must be synthetic-but-grounded: real geography, real fraud-type ratios, real amount distributions — fabricated individual complaint records.
Real, citable anchors used to calibrate the synthetic data
Known real-world mule-account/withdrawal-hub districts, widely reported in I4C briefings, news investigations, and Parliament answers: Jamtara & Deoghar (Jharkhand), Nuh & Mewat (Haryana), Bharatpur & Alwar (Rajasthan), Ahmedabad, parts of Bihar (Nawada).
NCRB "Crime in India" yearly reports — state/district-wise cybercrime counts.
I4C public numbers (press releases, PIB releases) — fraud-type breakdowns (UPI fraud, digital arrest scams, loan-app fraud, investment/trading scams, sextortion) and ₹-value stats.
RBI data — ATM/bank branch density by district, digital payment fraud trend reports.
Generation process
Generate a large batch of synthetic complaints (target: tens of thousands) with distributions (fraud-type frequency, amount ranges, time-of-day patterns) matching the real, cited sources above.
Deliberately seed a small set of complaints that share an identifier (same account/phone) across different states and dates, so the correlation engine has something real to detect in the live demo.
Every chart, number, and claim built on this data is labeled in the UI as "Synthetic data, calibrated to public NCRB/RBI figures" — this is a credibility feature, not a disclaimer to hide.

7. Machine Learning — Models, Training, Inference
7.1 Task 1 — Withdrawal Location Prediction
Type: multi-class ranking (top-3 output).
Features: sender bank, receiving IFSC, fraud type, amount, time-of-day, day-of-week, cluster-match flag (from graph engine), branch-level transaction velocity.
Model: XGBoost (gradient-boosted trees) — chosen over deep learning because the data is tabular, the dataset is comparatively small, and tree ensembles give native, checkable feature importances that directly power the explainability panel.
Output: top-3 ranked districts + confidence score.
7.2 Task 2 — Urgency / Countdown Estimation
Type: regression.
Trained on synthetic "time from complaint to historical cash-out" labels, calibrated against publicly reported mule-chain hop timing (funds typically clear 3–5 accounts within hours).
Output: estimated minutes remaining before likely cash-out — drives the visible countdown timer in the UI.
7.3 Two-Tier Prediction Logic (the cold-start fix)
A brand-new mule account with zero prior history is exactly the hardest — and most important — case to predict. Two tiers handle this:
Tier
When it triggers
What it uses
Tier 1 — Known identifier
Exact match found in the graph
Full cluster history: how fast this specific network has moved money before, past cash-out districts, victim count, hop count.
Tier 2 — Cold start
No prior match for this identifier
Behavioral/structural features only: IFSC branch cluster, transaction velocity (money leaving within minutes of arrival), amount-splitting patterns.
def predict(complaint, cluster_id):    if cluster_id and graph.has_history(cluster_id):        features = extract_cluster_features(cluster_id)      # Tier 1    else:        features = extract_branch_velocity_features(complaint)  # Tier 2    location_probs = model.predict_proba(features)    urgency_minutes = urgency_model.predict(features)    return top_k(location_probs, k=3), urgency_minutes
7.4 Explainability — real, not decorative
The "why" panel is generated from the trained model's own feature_importances_ (or SHAP values) at prediction time — never a hardcoded template sentence. This is checkable: a technically sharp judge asking "is this SHAP output or a canned string?" gets a truthful, defensible "it's pulled directly from the trained model."
def explain(complaint, prediction, model):    importances = model.feature_importances_    top_features = rank_features(importances, features)    return {        "matched_identifiers": get_matched_identifiers(complaint),        "top_drivers": top_features[:3],        "similar_pattern": describe_historical_match(complaint.cluster_id)    }

9. Feature Deep-Dive
9.1 (A2) Correlation / Cross-Complaint Graph Engine
Nodes = identifiers (phone, account, device ID, IFSC). Edges = "appeared together in complaint X." Before matching, identifiers are normalized (strip spaces, country codes, leading zeros) so formatting differences don't cause missed matches.
Critical guardrail: Matching happens ONLY on exact, specific identifiers (account number, phone, device ID) — never on generic fields like bank name or IFSC prefix alone, which would generate meaningless false-positive clusters shared by thousands of legitimate customers.
def correlate(complaint):    normalized = normalize_identifiers(complaint)    matches = graph.find_nodes(normalized)    if matches:        cluster_id = graph.get_cluster(matches[0])        graph.add_edge(complaint.id, matches[0])        return cluster_id    else:        graph.add_node(complaint.id, normalized)        return None
9.2 (C5) Prioritization Queue
Ranking is a weighted score, not a raw-amount sort:
priority_score = (    w1 * urgency_score  + w2 * normalized_recovery_amount   # log-scaled, so a Rs 15,000 case                                       # isn't invisible next to Rs 5 lakh  + w3 * cluster_size_bonus           # syndicate cases outrank equal-urgency                                       # lone complaints)
Why log-scaled amount: A linear amount weight always ranks a Rs 5 lakh case above a Rs 15,000 one — even if the smaller amount is an elderly victim's entire life savings and more urgent. Log-scaling lets urgency and cluster size compete fairly against raw rupee value.

9.4 (D8) Shared Fraud Registry / Permissioned Ledger
def flag_account(identifier, complaint_ref, bank_id):    if not complaint_ref:        raise Error("complaint reference is mandatory")    hashed = hmac_sha256(identifier, CONSORTIUM_SECRET_KEY)    ledger.append({        "hash": hashed, "status": "ACTIVE",        "complaint_ref": complaint_ref, "flagged_by": bank_id, "timestamp": now()    })def check_flag(identifier, bank_id):    hashed = hmac_sha256(identifier, CONSORTIUM_SECRET_KEY)    result = ledger.lookup(hashed)    return {"flagged": result.exists, "status": result.status}    # never returns which bank flagged it, complaint details, or victim info
Permissioned ledger (Hyperledger Fabric-style, banks/LEAs only as nodes) — NOT a public blockchain, since public chains leak transaction timing/metadata even with hashed content.
HMAC with a consortium-shared secret, not a bare hash — account number formats are semi-predictable, so a plain hash is reversible via a rainbow table.
Every flag write requires a mandatory complaint/FIR reference — never a unilateral bank decision.
A separate, logged "unflag" transaction, restricted to a supervisory role, so corrections are auditable.

10.1 How jurisdiction is determined
Reality check: Real LEA jurisdiction boundary data (which district cyber cell owns which pin code/IFSC range) is not accessible. A small, honestly-scoped static reference table (~10–15 real, publicly documented hotspot districts) is used instead of pretending to cover all of India.

The routing rule is deterministic logic, not ML. For any complaint, three locations are resolved:
Victim's location — from the complaint's filing address (always real).
Suspect account's bank branch location — from the IFSC code (public RBI data, genuinely accurate).
Predicted withdrawal location — from the ML model's output.
def route_jurisdictions(complaint, prediction):    jurisdictions = set()    jurisdictions.add(lookup_district(complaint.victim_address))    jurisdictions.add(lookup_district_from_ifsc(complaint.suspect_ifsc))    jurisdictions.add(prediction.top_predicted_district)    if complaint.cluster_id:        for linked in get_cluster_complaints(complaint.cluster_id):            jurisdictions.add(lookup_district(linked.victim_address))    return jurisdictions
Honest caveat: This reduces coordination LAG, it does not resolve legal jurisdiction AUTHORITY — e-FIR jurisdiction disputes are a real, documented bureaucratic issue this tool doesn't and can't fix.

What's real
What's mocked (and labeled as such)

The recipient — a mock inbox named "Mock Officer — Deoghar Cyber Cell," not a real official.

10.3 What "filing a case" actually means here
Not an FIR: The system never files a legal case or FIR. It generates a freeze-request document (account, IFSC, complaint references, cluster ID) explicitly labeled as requiring human/bank authorization. Nothing in the system unilaterally freezes an account or takes a legally binding action.

10.5 Threshold logic (alert-fatigue fix)
Not every complaint triggers the full alert cascade — only high-confidence/high-urgency ones do. Medium-confidence cases appear in the prioritization queue (visible, not push-notified). This is a deliberate, explainable design choice: precision over recall, because alert fatigue is a documented failure mode of proactive systems — officers start ignoring alerts within days if they fire too liberally, making the system as useless as the reactive one it replaced.

14. Every Loophole Identified — and Its Fix
This is the most important section for surviving judge Q&A. Read it fully — a team that has already thought through its own weak points beats a team with a fancier model and a confused answer, every time.
14.1 Data & Model Issues
Loophole
Fix / Framing
Reporting bias — complaint data only reflects fraud that got reported; elderly, rural, and ashamed victims under-report heavily, skewing “hotspots” toward urban, cyber-literate populations.
Normalize risk scores against district-level reporting-infrastructure access (internet penetration, banking density from Census/TRAI/RBI data) rather than raw complaint counts — a genuine, buildable “reporting-bias-adjusted risk score” feature.
Cold-start — the correlation engine only works once an identifier has appeared before; a brand-new mule account has zero history, which is exactly when prediction matters most.
Two-tier prediction: Tier 1 exact-match history, Tier 2 fallback to IFSC/branch-cluster and transaction-velocity features that don't require prior history (see Section 7.3).
Fuzzy identity matching — scammers use slight variants (different phone numbers, multiple mule accounts at the same branch); exact-match-only graph linking misses most real syndicate connections.
Normalize identifiers before matching (strip spaces/country codes/leading zeros) and match on device fingerprint/UPI handle similarity in addition to exact account number. Full fuzzy/entity-resolution matching stays a stated “next iteration.”
Alert fatigue — if alerts fire too liberally, officers start ignoring them within days (“cry wolf”), making the proactive system as useless as the reactive one it replaced.
High confidence threshold for auto-alerts; medium-confidence cases route to the visible queue only, not a push notification. Explicit precision-over-recall design stance, stated out loud in the pitch.
14.2 Ethical / Framing Issues
Loophole
Fix / Framing
Stigmatizing real districts — repeatedly naming Jamtara/Mewat/Nuh/Bharatpur as “hotspots” risks reading as blanket stigmatization of entire, mostly law-abiding populations.
Cluster ID (“Cluster #47”) is the primary UI label; district name appears only as secondary, cited supporting detail (“based on publicly reported LEA operations in this district”). The model flags account/transaction patterns, never geography or demographics, as an input.
Ledger governance — who has authority to flag an account? What if a flag is wrong (typo, mistaken linkage)? No dispute process risks a defamation-adjacent liability.
Every flag write requires a mandatory complaint/FIR reference number, never a unilateral bank decision. A separate, logged “unflag” transaction, restricted to a supervisory role, makes corrections auditable too.
Legal admissibility — a ledger hash does not automatically make evidence legally admissible; this is a common misconception.
Frame explicitly: “this strengthens chain-of-custody and complements, not replaces, Indian Evidence Act Section 65B certification.” Not fixable technically — only fixable through precise language.
14.3 System-Wide / Architectural Issues
Loophole
Fix / Framing
Adversarial adaptation — fraudsters can learn prioritization thresholds and structure transactions to stay under them (same evasion pattern as AML structuring).
Acknowledge openly as a known adversarial-ML problem; state the model needs periodic retraining/threshold rotation — signals maturity rather than a naive “solved forever” claim.
Jurisdiction mapping accuracy — no access to real, full LEA jurisdiction boundary data; getting it wrong routes alerts to the wrong desk, worse than not routing at all.
Use a small, honestly-labeled static table of ~10-15 well-documented real hotspot districts rather than claiming full coverage. Smaller-but-honest beats broad-but-fake.
Public-ledger metadata leakage — a public blockchain leaks transaction timing/metadata even with hashed account numbers; wrong architecture for regulated financial data.
Specify a permissioned ledger (Hyperledger Fabric-style, banks/LEAs only as nodes) — the correct, defensible architecture.
Hash reversibility — a bare hash of an account number is reversible via rainbow table, since formats are semi-predictable.
Use a keyed hash (HMAC with a consortium-shared secret) instead of a bare hash — a one-line fix that closes an obvious security hole.
Real bank buy-in — getting actual banks to join a shared ledger is a regulatory/business problem (RBI, NPCI approval), not something a hackathon build solves.
Be explicit: this is a pilot/proof-of-concept for a consortium model, not a claim that real banks have already onboarded.
Scale claims — the system has not been load-tested against the real 8,000 complaints/day volume.
State the architecture's scaling intent honestly (queue-based ingestion, stateless workers) without claiming a benchmark that wasn't run.
Autonomous action overclaim — implying the system can freeze funds by itself would be both legally incorrect and a much harder claim to defend.
Every enforcement-adjacent output (freeze request) is explicitly framed as a request requiring human/bank authorization, never an autonomous action.
NCRP/CFCFRMS integration — no real API access to these government systems exists.
State plainly: this is a mocked integration layer standing in for a real future API contract with I4C, which is exactly what a hackathon prototype should be.
15. Anticipated Judge Questions — Prepared Answers
Q: Is this legally allowed to auto-freeze accounts?
A: No — and we never claim it does. Every action is a request generated for human/bank authorization, never an autonomous action.
Q: What stops fraudsters from adapting once this is deployed?
A: Model drift and adversarial adaptation are real and acknowledged. The system is designed for a periodic retraining/threshold-rotation feedback loop, not a one-time trained model.
Q: How does this integrate with the actual NCRP/CFCFRMS systems?
A: We don't have access to those APIs, and we say so plainly. This is a mocked integration layer standing in for a real future API contract with I4C — exactly what a hackathon prototype should honestly represent.
Q: Can this actually handle 8,000 complaints a day?
A: We haven't load-tested it and don't claim to have. It's architected for horizontal scaling — stateless prediction workers, queue-based ingestion — but this is a proof of concept, not a production benchmark.
Q: Why blockchain, and why not just a database?
A: A regular database can't give competing banks a way to check a shared flag without a data-sharing agreement or exposing customer data to each other. A permissioned ledger (not a public blockchain) gives decentralized trust between institutions that don't otherwise trust each other with raw data — that's the actual reason it's used here, not because it's trendy.
Q: Does a hash on your ledger make evidence court-admissible?
A: No. It strengthens chain-of-custody and complements, but does not replace, Indian Evidence Act Section 65B certification requirements for electronic evidence.
Q: Isn't this just profiling certain districts as ‘crime hotspots’?
A: The model's primary output is a cluster ID tied to specific flagged account/transaction patterns, not a geography or demographic input. District names are shown only as secondary, cited context from public law-enforcement reporting, never as the basis for the prediction itself.
Q: What happens if a bank wrongly flags an innocent account?
A: Every flag requires a mandatory complaint/FIR reference — no unilateral bank decision. A supervisory-role-only “unflag” transaction is separately logged, so the correction itself is auditable.
Q: Is your accuracy number meaningful?
A: It's measured on synthetic data calibrated to public sources, and we say so directly rather than presenting it as validated real-world accuracy. We focus the pitch on time-saved and coordination speed rather than an accuracy percentage, because that's the actually defensible claim.
16. Limitations & Future Scope (Presentation Slide Content)

Limitations (be upfront about these)
Trained and demoed on synthetic data calibrated to public sources — not real NCRP data.
Jurisdiction mapping covers a small, honest set of documented hotspot districts, not all of India.
No load testing performed against real complaint volume.
Fuzzy/near-duplicate identity matching not yet implemented — exact-match only for MVP.
Real integration with NCRP/CFCFRMS and real bank consortium onboarding are both future, not current, steps.
Future Scope
Full fuzzy entity resolution across identifiers (phonetic name matching, near-duplicate detection).
Expanded, officially-sourced jurisdiction mapping in partnership with I4C.
Real API integration with NCRP / CFCFRMS.
Formal consortium onboarding process for banks joining the shared ledger.
Periodic model retraining pipeline to counter adversarial adaptation.
Load testing and horizontal scaling validation at production volume.

18. Glossary of Terms Used in This Project
Term
Meaning
NCRP
National Cybercrime Reporting Portal — the existing citizen-facing government complaint portal.
I4C
Indian Cyber Crime Coordination Centre — coordinates LEA action on cybercrime under the Ministry of Home Affairs.
CFCFRMS
Citizen Financial Cyber Fraud Reporting and Management System — the banking-side fund-blocking system.
Mule account
A bank account used to receive and quickly move stolen funds, often unknowingly owned by a third party.
Hop / hop chain
The sequence of accounts money passes through between the victim and final cash-out.
Cluster
A group of complaints linked by a shared identifier (account, phone, device ID), indicating a likely single syndicate.
Cold start
The case where a suspect identifier has no prior history in the system, making prediction harder.
HMAC
Keyed-hash message authentication code — a hash combined with a secret key, used here so hashed identifiers can't be reversed via rainbow tables.
Permissioned ledger
A blockchain-style ledger where only approved, known participants (banks/LEAs) can read/write — as opposed to a public blockchain.
Section 65B
The provision of the Indian Evidence Act governing admissibility of electronic evidence in court.
DPDP Act 2023
India's Digital Personal Data Protection Act, relevant to cross-jurisdiction sharing of victim PII.
